Understand Docksmith well enough to explain it

Docksmith is a simplified Docker-like build and runtime system written in Go with only the standard library. Each page here covers one part of the actual code: what it is, where it lives, how it works, how it talks to the rest, and what an interviewer is likely to ask.

The 30-second pitch

Say this first

"Docksmith reads a Docksmithfile with six instructions. Every COPY and RUN becomes an immutable tar layer named by its SHA-256 digest. A deterministic cache key (previous layer digest, instruction text, WORKDIR, ENV and, for COPY, file hashes) lets a warm rebuild skip every step. Containers run by re-executing the same binary inside new PID, mount, UTS, network and user namespaces, chroot-ing into the extracted layers and dropping capabilities. The same isolation function runs both RUN during a build and docksmith run. Layers are shared between images and deleted only when no manifest references them."

Unit 1 · Topic 1

What Docksmith is

A single Go binary that builds images from a Docksmithfile, stores them as content-addressed layers under ~/.docksmith/, and runs containers on Linux using chroot and namespaces. The README describes it as implementing "the core ideas behind Docker images, layers, and isolation — without external dependencies."

The five pieces, as the README lists them

The six instructions

InstructionProduces a layer?Effect (from builder.Build)

Example: the bundled sample app

# sample-app/Docksmithfile
FROM alpine:3.18
WORKDIR /app
COPY hello.sh /app/hello.sh
COPY data.txt /app/data.txt
ENV GREETING=Hello
RUN chmod +x /app/hello.sh
CMD ["/bin/sh", "/app/hello.sh"]

hello.sh prints $GREETING, the hostname, working directory and the contents of /app/data.txt. The base image alpine:3.18 is not pulled by Docksmith: scripts/setup-base-image.sh uses Docker once to export Alpine's filesystem and then calls docksmith import.

  1. go build -o docksmith .
  2. sudo ./scripts/setup-base-image.sh → docksmith import -t alpine:3.18 alpine-rootfs.tar
  3. sudo ./docksmith build -t myapp:latest ./sample-app (cold: every COPY/RUN shows [CACHE MISS])
  4. Build again (warm: [CACHE HIT]); edit data.txt and rebuild: that COPY and everything after it misses
  5. sudo ./docksmith run myapp:latest, then run -e GREETING=Goodbye myapp:latest

Requirements

Linux or WSL2, Go 1.21+ (go.mod: module docksmith, go 1.21), root (for chroot and namespaces). Docker is optional and used only by the setup and benchmark scripts. On other operating systems the code compiles but every runtime call returns docksmith runtime requires Linux (namespaces + chroot).

Not implemented (README)

seccomp, cgroups, overlayfs, volume mounts, container networking. Don't claim these in an interview.

In one or two sentences, what is Docksmith?

Answer: A simplified Docker-like build and runtime system written in Go with no external dependencies.

It builds images from a Docksmithfile into content-addressed tar layers with a deterministic build cache, and runs containers on Linux with chroot plus PID, mount, UTS, network and user namespaces, dropping capabilities in the child.

Which instructions create layers and which only change configuration?

Answer: Only COPY and RUN create layers.

FROM inherits the base image's layers and config. WORKDIR, ENV and CMD only update the builder's state (workdir, envState, cmdArgs), which ends up in the manifest's config. WORKDIR and ENV still matter for caching because they are part of later cache keys.

Docksmith has no registry client. How does the alpine:3.18 base image get into the store?

Answer: Through docksmith import, driven by scripts/setup-base-image.sh.

The script runs docker pull alpine:3.18, docker create, docker export to a tar, then docksmith import -t alpine:3.18 <tar>. import normalises the tar, stores it as one layer named by its SHA-256, and writes a manifest with empty Env/Cmd/WorkingDir. Docker is only needed for this one-time setup.

What happens if you run docksmith run myapp:latest on Windows or macOS?

Answer: It fails with "docksmith runtime requires Linux (namespaces + chroot)".

runtime/runtime_other.go has the build tag //go:build !linux and provides stub versions of Run, RunIsolated, ChildProcess and AssembleFilesystem that only return this error. A build with a RUN step fails the same way, but parsing, COPY layers, cache and store code still work, which is why most tests run on any OS.

Why does Docksmith need root privileges?

Answer: The README says root is "needed for chroot/namespace syscalls".

The runtime calls chroot, mounts proc and creates namespaces via clone flags. The setup script and examples all use sudo, and the Linux runtime test skips itself unless os.Getuid() == 0.

Which isolation features does Docksmith explicitly NOT implement?

Answer: seccomp, cgroups, overlayfs, volume mounts and container networking (README, "Isolation").

So there are no CPU/memory limits, no syscall filtering, layers are extracted into a directory instead of mounted with a union filesystem, and the network namespace leaves the container with no network.

Architecture

Eight Go packages under one module. main.go parses the CLI and calls into packages; builder is the hub of a build; store owns the on-disk layout; manifest and parser are leaf packages with no internal imports.

Two entry flows

Build

CLI: build -t name:tag ctx ↓ main.runBuild parser.Parse(ctx) ↓ []parser.Instruction builder.Build ↓ cache.ComputeCacheKey / Lookup ↓ layer.CreateCopyLayer | RunIsolated ↓ + layer.CreateRunLayer ↓ layer.StoreTar, cache.Store store.SaveManifest ↓ ~/.docksmith/images/name_tag.json

CLI: run [-e K=V] name:tag [cmd] ↓ main.runRun runtime.Run ↓ store.LoadManifest ↓ merge Env + overrides runtime.AssembleFilesystem ↓ layer.ExtractLayers → temp dir runtime.RunIsolated ↓ re-exec /proc/self/exe __child__ runtime.ChildProcess ↓ mount proc, chroot, caps user command → exit code

Design point to mention

Interview insight

When asked to draw the architecture, draw the two flows above, not the package list. Interviewers want to see the path of data: text → instructions → layers + cache entries → manifest → extracted rootfs → isolated process.

Which package is the "hub" of a build, and which packages does it call?

Answer: builder. It imports cache, layer, manifest, parser, runtime and store.

It reads []parser.Instruction, computes and looks up cache keys (cache), creates and stores layer tars (layer), runs RUN commands (runtime.RunIsolated), and saves the final manifest.Manifest through store.SaveManifest.

Which packages have no internal imports, and why does that matter?

Answer: parser and manifest import only the standard library.

They are pure data/translation layers. Everything else depends on them, but they depend on nothing, so there are no import cycles and they are trivial to unit-test (parser_test.go, manifest_test.go need no filesystem setup beyond temp data).

How do RUN during a build and docksmith run share code?

Answer: Both call runtime.RunIsolated(rootDir, command, workdir, envVars, useShell).

The builder passes the RUN text as a single-element slice with useShell=true, so the child runs /bin/sh -c "<text>". runtime.Run passes the image's CMD (or override) with useShell=false, so the child runs cmd[0] with cmd[1:] directly. Namespaces, chroot and capability dropping are identical.

Trace the call chain from docksmith build -t myapp:latest ./sample-app to the manifest on disk.

Answer: main → runBuild → parser.Parse(absContext) → builder.Build(instructions, BuildOptions{...}) → (per COPY/RUN) cache.ComputeCacheKey, cache.Lookup, layer creation, layer.StoreTar, cache.Store → store.SaveManifest → ~/.docksmith/images/myapp_latest.json.

runBuild resolves the context to an absolute path first with filepath.Abs.

Docksmith uses "no external dependencies". What does that cost and what does it buy?

Answer: It buys a self-contained codebase where every mechanism is visible; it costs hand-written code for things libraries would provide.

Implementation shows: argument parsing is hand-rolled per command; tar handling uses archive/tar; capset and prctl are called through raw syscall.Syscall with unsafe.Pointer; state is plain JSON files. Inference: for a learning project this makes every step explainable in an interview.

Which package knows the on-disk layout, and what is that layout?

Answer: store, via DocksmithDir, ImagesDir, LayersDir, CacheDir, LayerPath.

~/.docksmith/images/ holds one JSON manifest per image, layers/ holds tar files named sha256_<hex>.tar, and cache/index.json maps cache keys to layer digests. cache and layer get their paths from store rather than hard-coding them.

Name and tag parsing

parseNameTag scans from the right for the last colon. myapp:v2 → (myapp, v2); myapp → (myapp, latest). Implementation shows the parser's FROM handling instead splits on the first colon (strings.SplitN(args, ":", 2)), so the two only agree when the name has no colon.

run treats the first non-flag argument as the image and every later argument as the command override, so docksmith run myapp:latest /bin/sh -c "ls" overrides CMD.

Exit codes

any command error → stderr "Error: <err>" → exit 1 run, container ends → stdout "Container exited with code N" → exit N __child__ error → stderr "child process error: <err>" → exit 1 unknown command → "Unknown command: X" + usage → exit 1

Small helpers in main.go

  • formatSize: bytes → B / KB / MB / GB with one decimal under 10 (used by inspect).
  • normalizeTar: used only by import; see Import & tar normalisation.
Why is the __child__ check the very first thing in main()?

Answer: Because the same binary is re-executed as the container's first process, and in that role it must not behave as the CLI.

RunIsolated starts /proc/self/exe __child__ rootDir workdir mode cmd... with new namespace flags. When main sees __child__ it calls runtime.ChildProcess(args[1:]), which sets up the container and runs the command, then exits. A user would never type __child__.

What does docksmith run myapp (no tag) run, and what about docksmith run myapp:latest echo hi?

Answer: The first runs myapp:latest with the image's CMD; the second runs echo hi instead of CMD.

parseNameTag defaults the tag to latest. In runRun, the first non-flag argument becomes imageRef and the rest go into cmdOverride; runtime.Run uses the override when it is non-empty.

What exit code does the shell see after docksmith run if the container's command exits with 3?

Answer: 3.

The child calls os.Exit(exitErr.ExitCode()); RunIsolated converts the parent's *exec.ExitError into (3, nil); main prints Container exited with code 3 and calls os.Exit(exitCode). Errors before the container starts (e.g. image not found) exit 1.

How does main.go parse flags, and what is one quirk of that approach?

Answer: Manually: each runX loops over args with an index and a switch, no flag package.

Quirk in run: the -e case is checked before anything else at every position, so a command override can never contain a literal -e. docksmith run img grep -e foo fails with -e requires KEY=VALUE format, got: foo. For build, a second positional argument is rejected with unexpected argument.

FROM registry:5000/app:v1 and docksmith run registry:5000/app:v1 would not refer to the same image. Why?

Answer: The two code paths split name and tag differently.

parseNameTag in main.go uses the last colon → name registry:5000/app, tag v1. The parser's FROM uses strings.SplitN(args, ":", 2) → name registry, tag 5000/app:v1. Docksmith has no registry support, so this is an edge case, but it is a real inconsistency.

What does docksmith prune do, and which packages does it call?

Answer: It deletes layer files referenced by no manifest, then deletes cache entries whose layer file no longer exists.

runPrune calls store.PruneOrphanLayers() then cache.PruneStale() and prints both counts. Order matters: pruning layers first lets the cache step clean up entries that pointed to the layers just removed.

Parser: Docksmithfile → instructions

parser/parser.go turns the text of <context>/Docksmithfile into a validated []Instruction. It does no I/O beyond reading that one file, and every error names a line number.

Why the builder needs it

The builder never looks at raw text. It switches on Instruction.Type and reads pre-split fields (CopySrc, EnvKey, CmdArgs, …). The raw line is kept as FullText because it is part of the cache key and becomes the layer's createdBy.

The data structure

type InstructionType int   // InstrFROM, InstrCOPY, InstrRUN, InstrWORKDIR, InstrENV, InstrCMD (iota) + String()
type Instruction struct {
    Type      InstructionType
    Args      string    // everything after the keyword, trimmed
    Line      int       // 1-based line number
    FullText  string    // the trimmed source line → cache key + createdBy
    CmdArgs   []string  // CMD
    CopySrc, CopyDst    string  // COPY
    EnvKey, EnvValue    string  // ENV
    FromImage, FromTag  string  // FROM
}

How it works

  1. Parse(contextDir) reads filepath.Join(contextDir, "Docksmithfile") and calls ParseContent.
  2. Split on \n; strings.TrimSpace each line (this also removes a trailing \r). Skip empty lines and lines starting with #.
  3. parseLine: split once on the first space → keyword (upper-cased, so run works) + args.
  4. Per-keyword validation and splitting (table below). Unknown keyword → unrecognised instruction "X".
  5. After all lines: empty file → Docksmithfile is empty; first instruction not FROM → line N: first instruction must be FROM.
KeywordParsing ruleError when
FROMSplitN(args, ":", 2) → image, tag (default latest)no argument
COPYstrings.Fields(args) must give exactly 2 → src, dstnot exactly two fields

Worked example

            FullText: "ENV GREETING=Hello", EnvKey: "GREETING", EnvValue: "Hello"}

Edge behaviour the code shows

  • Implementation shows the separator is a single space: RUN\techo hi becomes keyword RUN\tECHO → unrecognised.
  • No line continuations (\): each physical line is one instruction.
  • ENV values are not unquoted: ENV A="x y" stores "x y" including the quotes.
  • COPY paths can't contain spaces and only one source is allowed.
  • A second FROM later in the file is not rejected by the parser (the builder would append the second base's layers too).
  • Comments and blank lines are dropped, so editing them does not change any FullText and therefore no cache key.
What does the parser produce, and which fields does the builder rely on?

Answer: A slice of parser.Instruction structs, one per non-comment line.

The builder switches on Type and uses FromImage/FromTag, CopySrc/CopyDst, Args (RUN text, WORKDIR path), EnvKey/EnvValue, CmdArgs, and FullText for the cache key and the layer's CreatedBy.

Why does CMD have to be a JSON array while RUN is free text?

Answer: Because they are executed differently.

Implementation shows: RUN is passed to RunIsolated with useShell=true and run as /bin/sh -c "<text>", so a single string is correct. CMD is run with useShell=false: exec.Command(cmd[0], cmd[1:]...), which needs the program and arguments already split. Parsing JSON gives that exact split without guessing at quoting rules.

You add a comment line above a RUN step and rebuild. Does the RUN step miss the cache?

Answer: No.

Comment lines are skipped in ParseContent and never become instructions. The RUN's FullText is unchanged and Line is not part of the cache key, so the key and the cache hit are the same. Changing whitespace inside the RUN line would change FullText and cause a miss.

What does the parser do with COPY my file.txt /app/?

Answer: It rejects it: line N: COPY requires exactly two arguments (src dest).

COPY uses strings.Fields, which splits on whitespace, giving three fields. There is no quoting or JSON form for COPY, so paths with spaces aren't supported.

How is ENV KEY=a=b parsed?

Answer: Key KEY, value a=b.

The parser uses strings.Index(args, "="), the first =, and trims both sides. Only an empty key or a missing = is an error. Quotes are not stripped.

Which validation does the parser do across lines (not per line)?

Answer: Two checks after all lines are parsed: the file must contain at least one instruction, and the first one must be FROM.

Errors: Docksmithfile is empty and line N: first instruction must be FROM. Per-line checks happen earlier and stop at the first bad line.

A Docksmithfile written on Windows has CRLF line endings. Does it parse?

Answer: Yes.

Content is split on \n, then each line goes through strings.TrimSpace, which removes the trailing \r. Keywords are also upper-cased, so case doesn't matter either.

Builder: the build loop

builder.Build(instructions, opts) in builder/builder.go walks the instructions once, in order, carrying a small amount of state. Only COPY and RUN touch the cache and produce layers; the rest edit state. At the end it writes one manifest.

Build state

VariableMeaningChanged by
layers []manifest.LayerImage layers so far, bottom firstFROM (append base layers), COPY, RUN
workdir stringCurrent working directoryFROM (inherit), WORKDIR
envState map[string]stringEnv varsFROM (inherit), ENV

Per-instruction behaviour

  • FROM: store.LoadManifest(image, tag); error step i/N: FROM x:y: image x:y not found if missing. Base Env entries are split on the first = into envState.
  • COPY: layer.GetSourceFileHashes → key → lookup → on miss layer.CreateCopyLayer(ctx, src, dst, workdir) → layer.StoreTar → cache.Store (unless NoCache).
  • RUN: key without file hashes → on miss: os.MkdirTemp("", "docksmith-build-*"), layer.ExtractLayers of every layer so far, MkdirAll(workdir), layer.SnapshotDir, build sorted env (+ default PATH if unset), runtime.RunIsolated(tmpRoot, []string{instr.Args}, workdir, envVars, true), layer.CreateRunLayer, StoreTar, remove temp dir, cache.Store.
  • After either: layer size from os.Stat(store.LayerPath(digest)); append {Digest, Size, CreatedBy: FullText}; print Step i/N : <line> [CACHE HIT|MISS] 0.00s.

Finishing the build

Env is written as sorted K=V strings. created is time.Now() unless every step hit the cache and a manifest with this name:tag already existed, in which case the old timestamp is kept. Inference: because the manifest digest is a hash of its JSON including created, keeping the timestamp makes a fully cached rebuild produce the same image digest.

Failure points

Missing base image; COPY source not found or glob matching nothing; RUN exiting non-zero (RUN command exited with code N); I/O errors while extracting or storing. Every RUN failure path calls os.RemoveAll(tmpRoot) before returning. Layers already written by earlier steps stay on disk (see prune).

What is prevDigest right after a FROM step, and why does that matter?

Answer: The base image's manifest digest (baseManifest.Digest), not a layer digest.

It seeds the first cache key. Inference: since the manifest digest covers the whole manifest JSON including created, re-importing the same base tar at a different time gives a new manifest digest, so every following step misses even though the layer bytes are identical.

What is "cascade miss" and how is it implemented?

Answer: After the first COPY/RUN cache miss, all later COPY/RUN steps are rebuilt without looking up the cache.

cascadeMiss starts as opts.NoCache; the lookup runs only if !cascadeMiss; any miss sets it true. The README states it as "Cache misses cascade to all subsequent steps."

In the sample app you edit data.txt and rebuild. Which steps hit and which miss?

Answer: COPY hello.sh hits; COPY data.txt misses; RUN chmod +x /app/hello.sh misses.

The data.txt COPY key includes the file's content hash, which changed. That sets cascadeMiss, so the RUN is rebuilt without a lookup. FROM, WORKDIR, ENV and CMD never use the cache. This is demo step 3 in the README.

Walk through what the builder does for a RUN step on a cache miss.

Answer: Temp root → extract all layers → ensure WORKDIR → snapshot → run isolated → diff into a tar → store → cache.

  1. os.MkdirTemp("", "docksmith-build-*")
  2. layer.ExtractLayers(tmpRoot, digests) for every layer so far
  3. os.MkdirAll(tmpRoot/workdir)
  4. layer.SnapshotDir → before map
  5. sorted env + default PATH; runtime.RunIsolated(tmpRoot, []string{instr.Args}, workdir, env, true); non-zero exit is an error
  6. layer.CreateRunLayer(tmpRoot, before) → tar + digest; StoreTar; remove temp; cache.Store
Why does the builder keep the old created timestamp when every step hits?

Answer: So a fully cached rebuild writes an identical manifest.

Implementation shows: created = now unless allCacheHit && existingCreated != "". Inference: manifest.ComputeDigest hashes the JSON including created, so without this a no-op rebuild would change the image ID on every run.

What happens with docksmith build --no-cache?

Answer: Every COPY and RUN is rebuilt and no cache entries are written.

cascadeMiss starts true, so no lookups; and both cache.Store calls are guarded by if !opts.NoCache. Layers are still stored (and deduplicated by digest in StoreTar), and the manifest is written as usual.

A RUN step fails halfway through a build. What is left on disk?

Answer: Layers from earlier steps and their cache entries; no manifest; no temp dir.

The RUN error path calls os.RemoveAll(tmpRoot) and returns step i/N: RUN command exited with code N. store.SaveManifest runs only at the end, so the image is not created or updated. Earlier layers become orphans unless another image references them; docksmith prune removes them.

Which env does a RUN command see, and in what order?

Answer: Every K=V in envState (base image env + ENV lines so far), sorted, plus a default PATH if PATH isn't set.

Default: /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin. The list is set as cmd.Env on the re-exec, and ChildProcess passes os.Environ() on to the command.

Unit 2 · Topic 3

Build cache

cache/cache.go answers one question for each COPY/RUN: "have we built exactly this step before?" It hashes the inputs that determine the step's output into a key, and stores key → layer digest in ~/.docksmith/cache/index.json.

Why each input is there

InputWhat a change means
prevDigestAnything earlier in the build changed → this step's starting filesystem changed
FullTextThe instruction itself was edited
workdirRelative COPY destinations and the RUN cwd depend on it
envA RUN command may read env vars
file hashes (COPY)The copied content changed even though the line didn't

Determinism: serializeEnvState and serializeFileHashes sort keys/paths first, because Go map iteration order is random. Without sorting, the same build could produce different keys.

The index and its operations

type Index struct { Entries map[string]string `json:"entries"` }
var mu sync.Mutex      // guards every load/save in this process
FunctionBehaviour
Lookup(key)Load index; return the digest only if the key exists and store.LayerExists(digest); otherwise ""
Store(key, digest)EnsureDirs, load, set, write the whole file (MarshalIndent)
PruneStale()Delete entries whose layer file is missing; save if anything was removed
loadIndexMissing file → empty index; unparseable JSON → empty index, no error
HashFile(path)SHA-256 hex of a file; exported, used by cache_test.go (the builder uses layer.GetSourceFileHashes)
Self-healing lookups

Because Lookup checks that the layer file exists, deleting layers (via rmi) can never produce a hit that points to nothing. The step is simply rebuilt. prune tidies the dangling entries.

Gaps visible in the code

Implementation shows: (1) serializeFileHashes writes only hashes, not paths, so renaming a file inside a copied directory (same content) gives the same key. (2) File mode isn't in the key. (3) Fields are concatenated with no separator. (4) The mutex only protects one process; two concurrent builds could overwrite each other's index writes.

List the inputs to a Docksmith cache key and justify each.

Answer: prevDigest, instruction text, workdir, sorted env, and for COPY the source file hashes.

prevDigest captures every earlier change; text captures edits to the step; workdir affects relative paths and the RUN cwd; env can change RUN output; file hashes catch content changes that don't change the COPY line. All are fed into one SHA-256 in that order.

Why does serializeEnvState sort the keys?

Answer: Go randomises map iteration order.

Iterating envState directly could emit A=1\nB=2 one run and B=2\nA=1 the next, giving different keys for identical input and breaking the cache. Sorting makes the serialisation, and so the key, deterministic. serializeFileHashes sorts paths for the same reason.

A cache entry exists, but its layer file was deleted by rmi. What happens on the next build?

Answer: A cache miss; the step is rebuilt.

Lookup returns "" when store.LayerExists(digest) is false. The rebuild calls cache.Store with the same key, overwriting the stale entry. docksmith prune would otherwise remove the entry via PruneStale.

Why hash file contents for COPY instead of checking modification times?

Answer: Content hashes change exactly when content changes.

Implementation shows GetSourceFileHashes computes SHA-256 per matched file. Inference: mtimes change on checkout or copy without a content change (false misses) and can stay the same after an edit (false hits). The cost is reading every source file on every build.

You rename files/a.txt to files/b.txt (same content) and the build uses COPY files /data/. What does the cache do, and is that correct?

Answer: It hits, which is wrong: the image would still contain a.txt.

The COPY line didn't change, prevDigest/workdir/env didn't change, and serializeFileHashes concatenates only hashes (sorted by path), which are identical. Fix: include each path (and mode) in the serialisation, e.g. path:hash.

What if index.json is corrupted?

Answer: Docksmith silently treats it as empty: every lookup misses.

loadIndex returns a fresh empty Index when json.Unmarshal fails. The next Store writes a new valid file containing just that entry, so the old entries are lost but the build still works.

Is the cache safe if two docksmith build processes run at once?

Answer: Not fully.

The sync.Mutex is per process. Each Store reads the whole file, adds one entry and rewrites it with os.WriteFile, so two processes can interleave and one's entry is lost. Inference: the result is extra cache misses, not wrong images, because Lookup still verifies the layer exists. A file lock plus write-to-temp-and-rename would fix it.

Why don't WORKDIR, ENV or CMD have cache entries of their own?

Answer: They produce no layer, so there's nothing to reuse.

They only update builder state. WORKDIR and ENV still influence caching because they are inputs to the keys of later COPY/RUN steps. CMD is not part of any key since it doesn't affect the filesystem.

Unit 2 · Topic 4

COPY layers & globbing

layer.CreateCopyLayer(contextDir, src, dst, workdir) resolves which context files match src, decides where each lands, and writes them into a deterministic tar whose SHA-256 is the layer digest. It never runs a container.

Step by step

  1. Resolve sources (resolveSourceFiles): if src contains any of * ? [ ] → globUnderDir; else stat it: a file → itself; a directory → every file under it (walk), skipping Docksmithfile, .git and .docksmith.
  2. No matches → COPY <src>: no files matched.
  3. Destination: absolute dst as-is; relative → joined to workdir, or to / if no workdir.
  4. Directory or file? isDstDir = dst ends with "/" || more than one source file. Directory → dest/<basename>; file → dest.
  5. Sort sources; for each, write a tar header with Mode = perm bits, ModTime = zero, Uid = Gid = 0, then the bytes. Leading / is stripped from tar names.
  6. Digest = "sha256:" + hex(SHA-256(tar bytes)).

Source says (comment) parent directory headers are intentionally not written, "This keeps WORKDIR 'silent creation' from being stored as a tar delta."

** glob matching

globUnderDir walks the context and tests each file's slash-separated relative path with matchSegments:

if pat[0] == "**" {   // zero or more segments
    try pat[1:] against segs, segs[1:], segs[2:], ...
}
else filepath.Match(pat[0], segs[0]) && matchSegments(pat[1:], segs[1:])
Example

Pattern **/*.txt against b.txt: ** matches zero segments, *.txt matches b.txt ✓. Against sub/a.txt: ** consumes sub, then *.txt matches ✓. This is TestCreateCopyLayerGlob.

Behaviour worth knowing

Directory structure is flattened

Implementation shows: resolveSourceFiles returns files, never directories, and the tar path for a directory destination is destPath + "/" + filepath.Base(relPath). So COPY src /app/ with src/a/x.txt and src/b/y.txt produces /app/x.txt and /app/y.txt; two files with the same basename collide. The fi.IsDir() branch that calls addDirFilesToTar is effectively unreachable from this path.

  • The skip list (Docksmithfile, .git, .docksmith) applies only to directory sources, not to globs: COPY * /app/ would include the Docksmithfile.
  • COPY dir /app (no trailing slash) where dir holds exactly one file writes that file as /app.
  • Only permission bits are kept; symlinks in the context are followed (os.Stat / os.ReadFile).
How does CreateCopyLayer decide whether dst is a directory?

Answer: isDstDir := strings.HasSuffix(dst, "/") || len(srcFiles) > 1.

If true, each file lands at dest/<basename>; otherwise the single file is written at dest itself. So COPY hello.sh /app/hello.sh writes app/hello.sh, and COPY hello.sh /app/ writes app/hello.sh too.

Why are tar headers written with zero ModTime and uid/gid 0?

Answer: So the same input files always produce byte-identical tars, and therefore the same digest.

Source says (README): "Reproducible tars: all tar entries sorted lexicographically, timestamps zeroed, uid/gid set to 0". The digest is the layer's name, so a stable digest is what makes deduplication in StoreTar and reuse across builds work.

What does COPY src /app/ produce if src/ contains a/config.json and b/config.json?

Answer: Two tar entries both named app/config.json; after extraction only the later one survives.

Directory sources are expanded to files, and each file's tar path uses only filepath.Base. Sorted order puts src/b/config.json second, so it overwrites the first during extraction. A fix would keep the path relative to the source directory.

Explain how matchSegments handles **.

Answer: It tries matching the rest of the pattern against the remaining segments after skipping 0, 1, 2, … segments.

First it tries pat[1:] against all of segs (zero segments), then against segs[i+1:] for each i. Any success returns true. Normal segments use filepath.Match on one segment at a time, so * never crosses a /.

Where does a relative COPY destination end up?

Answer: Under the current WORKDIR, or under / if none is set.

destPath = filepath.Join(workdir, dst) when dst isn't absolute and workdir != ""; otherwise "/" + dst. That is why workdir is part of the COPY cache key.

What happens with COPY *.md /docs/ when no Markdown files exist?

Answer: The build fails with COPY *.md: no files matched.

The builder first calls layer.GetSourceFileHashes; a glob with zero matches is not an error there (empty map), so a key is computed and looked up. On the miss, CreateCopyLayer sees zero files and returns the error, wrapped as step i/N: COPY: …. A non-glob source that doesn't exist fails earlier, in the hashing call: step i/N: COPY hash source files: source x not found: ….

Why doesn't a COPY layer include directory entries for /app?

Answer: Source says it's intentional, to keep "WORKDIR silent creation" out of the tar delta.

Extraction calls os.MkdirAll(filepath.Dir(target)) before writing each regular file, so parent directories are created anyway. Leaving them out means the layer contains only the copied files.

RUN layers: snapshot, diff, whiteouts

A RUN step can change any file, so Docksmith captures its effect by comparing the filesystem before and after. layer.SnapshotDir records the "before"; layer.CreateRunLayer walks the "after", finds additions, modifications and deletions, and writes them as a delta tar.

Snapshot

SnapshotDir(root) walks the tree and returns map[relPath]string: "dir" for directories, the SHA-256 hex of the contents for everything else (empty string if hashing fails). proc, dev, sys subtrees are skipped.

What the diff misses

Implementation shows: (1) Changes are detected by content hash only, so a mode-only change such as the sample app's RUN chmod +x /app/hello.sh isn't captured; that layer has no entry for hello.sh. The sample still runs because CMD is ["/bin/sh", "/app/hello.sh"]. (2) The walk runs on the host and os.ReadFile follows symlinks, so symlinks created by RUN are not stored as symlinks; an absolute link target resolves against the host filesystem. (3) A deleted directory gets an opaque marker plus a whiteout per file inside, so after extraction the directory still exists, empty. (4) Opaque markers are written by ranging over a Go map, so with several deleted directories their order is not deterministic.

Why can't a RUN layer be built the way a COPY layer is?

Answer: A COPY knows its files up front; a RUN command can create, change or delete anything.

So the builder extracts the image so far into a temp root, snapshots it, runs the command in isolation, and CreateRunLayer compares the result with the snapshot to find exactly what changed.

What does SnapshotDir store for each path, and which paths does it skip?

Answer: "dir" for directories and the SHA-256 hex of file contents for everything else; it skips proc, dev and sys subtrees.

Skipping them keeps the runtime's own proc mount point and dev directory (created by RunIsolated) out of layers.

What is a whiteout and why is it needed?

Answer: An empty tar entry named .wh.<name> that means "this path was deleted".

Layers are immutable and applied in order. A deletion in layer 3 can't remove bytes from layer 1's tar, so layer 3 records a marker; when layers are extracted bottom-up, the marker removes the path that lower layers created. The README calls these "Docker-style whiteout entries".

The sample's RUN chmod +x /app/hello.sh layer is almost empty. Why, and why does the app still work?

Answer: The diff only compares content hashes, and chmod changes the mode, not the content.

CreateRunLayer includes a file only if it is new or its hash differs, so hello.sh is left out. The app works because CMD runs /bin/sh /app/hello.sh, which doesn't need the execute bit. Fix: snapshot hash + mode.

In what order are entries written into a RUN layer tar?

Answer: Opaque directory markers, then file whiteouts (sorted), then changed/new paths in sorted order with parent directory headers.

ensureParentDirs writes a TypeDir header (mode 0755) for each missing parent once, tracked in addedDirs. Implementation shows one gap in determinism: opaque markers are emitted with for dirPath := range deletedDirs, a map, so when a RUN deletes two or more directories their order (and so the tar bytes and digest) can differ between runs.

A RUN step does rm -rf /var/cache/apk. What does the layer contain, and what do you see after extraction?

Answer: An opaque marker var/cache/apk/.wh..wh..opq plus .wh. entries for each removed file below it; after extraction /var/cache/apk exists but is empty.

The before-map has var/cache/apk as "dir", and every file under it is also in deletedPaths. The opaque marker empties the directory but never removes the directory itself.

Why might a symlink created by RUN (e.g. ln -s /bin/busybox /usr/bin/foo) not survive into the layer correctly?

Answer: CreateRunLayer reads every non-directory with os.ReadFile, which follows symlinks, and the walk runs on the host, outside the chroot.

An absolute target like /bin/busybox resolves against the host, not the image, so the layer gets a regular file with host content, or the entry is skipped if the read fails. Extraction does support TypeSymlink, but RUN layers never write one.

Images & manifests

In Docksmith an image is a JSON manifest: a name, tag, digest, creation time, a small config (Env, Cmd, WorkingDir) and an ordered list of layer references. The layer bytes live separately in layers/. The manifest file comment calls it "the 'source of truth' that describes what an image is made of".

The types (manifest/manifest.go)

What myapp:latest looks like (shape)

  "digest": "sha256:…", "created": "2026-…Z",

  "layers": [
    { "digest": "sha256:…", "size": …, "createdBy": "import alpine-rootfs.tar" },
    { "digest": "sha256:…", "size": …, "createdBy": "COPY hello.sh /app/hello.sh" },
    { "digest": "sha256:…", "size": …, "createdBy": "COPY data.txt /app/data.txt" },
    { "digest": "sha256:…", "size": …, "createdBy": "RUN chmod +x /app/hello.sh" }
  ]
}

The first layer comes from the base image via FROM. createdBy is the instruction's FullText, or import <file> for imported bases.

The image digest

  1. ComputeDigest(m) sets m.Digest = "".
  2. json.Marshal(m) (compact; Go writes struct fields in declaration order).
  3. sha256.Sum256 of those bytes → m.Digest = "sha256:<hex>".
  4. store.SaveManifest then writes the indented JSON (Serialize = MarshalIndent).

ShortID(m) = m.Digest[7:19], the 12 hex chars after sha256:, shown by images and the "Successfully built" line.

What the digest covers

Everything in the manifest except the digest field itself: name, tag, created, config and layer list. So the same layers under a different tag, or rebuilt at a different time, produce a different image digest. That's why the builder preserves created on a fully cached rebuild.

Where images are stored

store.manifestFilename(name, tag) replaces / and : with _ in both parts and returns <name>_<tag>.json in ~/.docksmith/images/. Saving an image with an existing name:tag overwrites the file.

Edge case

Implementation shows: because _ is also the separator, a_b:c and a:b_c both map to a_b_c.json and would overwrite each other. LoadManifest does not re-verify the digest when reading.

What is an "image" in Docksmith, concretely?

Answer: A JSON manifest file in ~/.docksmith/images/ that lists layer digests (bottom first) plus Env, Cmd and WorkingDir.

The layers themselves are tar files in layers/, referenced by digest. Running an image means extracting those tars in order and applying the config.

How is the manifest digest computed, and why is the digest field blanked first?

Answer: Set Digest = "", json.Marshal the struct, SHA-256 the bytes, store the hex as sha256:….

A hash can't include itself, so the field must have a fixed value while hashing. Using the empty string means anyone can recompute it: blank the field, re-marshal, hash, compare.

You build the same Docksmithfile twice with no changes. Is the image ID the same?

Answer: Yes, if every step hits the cache.

Layer digests are identical, and the builder keeps the existing created when allCacheHit, so the marshalled manifest is byte-identical and so is its SHA-256. If any step misses, created becomes the current time and the ID changes even if the new layers happen to be identical.

Does a derived image reference its base image, or the base's layers?

Answer: The base's layers, copied into its own layer list.

In FROM, the builder does layers = append(layers, baseManifest.Layers...). The derived manifest is self-contained: removing the base manifest later doesn't break it, and the shared layer files survive because the derived manifest still references them.

How are manifest file names derived, and what's a weakness?

Answer: <name>_<tag>.json with / and : replaced by _.

Weakness: the mapping isn't reversible, so different name:tag pairs can share a file (a_b:c vs a:b_c). images still shows the right name and tag because it reads them from the JSON, not the file name.

What does createdBy hold and who uses it?

Answer: The instruction line that produced the layer (FullText), or import <file> for an imported base.

It's informational: docksmith inspect prints it as CREATED BY under each layer. It plays no part in caching or extraction.

Unit 3 · Topic 2

Layers: storage, sharing, extraction

A layer is an immutable tar of filesystem changes, named by the SHA-256 of its bytes. Images share layers by digest. To get a usable root filesystem, Docksmith extracts every layer of an image, in order, into one directory, applying whiteouts as it goes.

Writing a layer

layer.StoreTar(tarBytes, digest): EnsureDirs; if the file already exists, return immediately ("immutable — already exists"); else os.WriteFile. Because the name is the hash of the content, an existing file with that name already has the right bytes. TestStoreTarIsImmutable covers this.

Extracting layers: ExtractLayers(targetDir, digests)

Calls extractTar for each digest in order (bottom first). Per tar entry:

  1. cleanName = filepath.ToSlash(filepath.Clean(hdr.Name)); skip names starting with ...
  2. Opaque marker → remember the dir, delete everything inside it in targetDir.
  3. .wh.<name> → remember the hidden path, os.RemoveAll it.
  4. Entry under a path whited-out earlier in this same layer → skip (drain its data).
  5. Otherwise by type: dir → MkdirAll; regular → MkdirAll parent, create/truncate with the header's mode, copy bytes; symlink → remove + os.Symlink; hard link → remove + os.Link to targetDir/Clean(Linkname); anything else (devices, fifos) → skipped.

Who extracts, and when

CallerTargetLifetime
builder.Build (RUN miss)os.MkdirTemp("", "docksmith-build-*")Removed after the layer is stored or on error
runtime.AssembleFilesystem (run)os.MkdirTemp("", "docksmith-run-*")defer os.RemoveAll in runtime.Run

Source says (README) overlayfs is not implemented. Inference: the cost is copying the full image for every RUN miss and every run, in exchange for simplicity and no extra mount handling.

Extraction caveats in the code

Only ..-prefixed names are rejected; a layer could create a symlink and then write a file through it, escaping targetDir. Several errors are ignored (MkdirAll, io.Copy, os.Symlink, os.Link). Whiteout bookkeeping is per layer (fresh maps for each extractTar call).

What is a layer in Docksmith and how is it named?

Answer: An immutable tar of filesystem changes from one COPY, RUN or import, named sha256:<hex of the tar bytes>.

On disk it's ~/.docksmith/layers/sha256_<hex>.tar (store.LayerPath replaces : with _). Manifests refer to layers only by this digest.

Why can StoreTar skip writing when the file already exists?

Answer: The file name is the SHA-256 of the content, so an existing file with that name already holds those exact bytes.

This gives free deduplication: two images or two builds producing the same layer share one file. It also means layer files are never modified, only created and (by GC) deleted.

Walk through what extractTar does with a .wh.old entry and with the entries after it.

Answer: It deletes the hidden path from the target directory and skips any later entries for that path in the same tar.

IsWhiteout matches; HiddenPathFromWhiteout turns tmp/.wh.old into tmp/old; it is added to the whiteouts map and removed with os.RemoveAll. shouldSkipDueToWhiteout then drops any later entry equal to that path (or under an opaque dir).

Layer 1 has etc/motd; layer 3 writes a new etc/motd. Which version does a container see?

Answer: Layer 3's.

ExtractLayers applies layers in manifest order. When layer 3's regular-file entry is extracted, os.OpenFile(..., O_CREATE|O_WRONLY|O_TRUNC, mode) truncates and rewrites the file. "Last layer wins" is the stacking rule.

Is extractTar safe against a malicious layer?

Answer: Only partly.

It rejects names that start with .. after filepath.Clean, which stops ../../etc/passwd. But a layer could first create a symlink x → / and then write x/etc/passwd; the code doesn't check that resolved targets stay inside targetDir. Hard-link targets aren't validated either. In practice layers come from your own builds or imports.

Docksmith extracts layers into a temp directory instead of mounting them. What's the trade-off?

Answer: Simpler and self-contained, but it copies the whole image for every RUN miss and every docksmith run.

Source says overlayfs is "Not implemented". Implementation shows both builder.Build and runtime.AssembleFilesystem call ExtractLayers into a fresh os.MkdirTemp directory and delete it afterwards. Writes in a container therefore go to a throwaway copy and never reach the host or the stored layers.

The Alpine base layer contains device files (e.g. dev/null, if present in the export). What does extraction do with them?

Answer: Skips them.

extractTar handles only TypeDir, TypeReg, TypeSymlink and TypeLink; the default case drains any data and moves on. RunIsolated creates an empty dev directory but no device nodes, so /dev/null doesn't exist as a device inside the container.

Why compute instead of store counts?

Inference: manifests are the single source of truth. A stored counter could disagree with them after a crash between two writes; a scan can't. The cost, a read of every manifest per rmi/prune, is small at this scale.

How does rmi avoid deleting layers another image still needs?

Answer: It counts how many times each layer digest appears across all manifests and deletes a layer only when its count drops to zero.

Where are reference counts stored?

Answer: Nowhere; they are recomputed on demand.

LayerReferences calls ListManifests and increments refs[l.Digest] for every layer of every manifest. Both RemoveImage and PruneOrphanLayers call it, so counts always match the manifests on disk.

How can orphan layers appear if rmi already cleans up?

Answer: From work that never produced (or no longer has) a manifest.

A build that fails partway leaves the layers of earlier steps. Rebuilding a tag overwrites its manifest, so layers only the old version used lose their last reference without anyone deleting them. prune sweeps all such zero-reference files.

How does PruneOrphanLayers get a digest back from a file name?

Answer: digestFromLayerFilename: require the .tar suffix, strip it, and replace the first _ with :.

sha256_ab12….tar → sha256:ab12…. Files without .tar (and directories) are ignored.

You rmi alpine:3.18 after building myapp from it. Does myapp still run?

Answer: Yes.

myapp's manifest lists the Alpine layer digest itself (FROM copied it), so that layer's count stays ≥ 1 and the file is kept. Only the alpine_3.18.json manifest disappears. Building a new image FROM alpine:3.18 would then fail with image alpine:3.18 not found.

How do the tests avoid touching your real ~/.docksmith?

Answer: store.SetHomeForTest(dir) sets homeOverride, and DocksmithDir() uses it instead of the user's home.

Tests pass t.TempDir(), so every manifest, layer and cache file goes to a temp directory that Go deletes after the test. Since cache and layer get paths from store, one call redirects everything.

Import & tar normalisation

docksmith import -t name:tag rootfs.tar (implemented in main.runImport) is the only way a base image enters the store. It rewrites the tar into a canonical form so the same filesystem always gives the same layer digest.

Flow

rootfs.tar (e.g. from docker export) ↓ os.ReadFile (whole file in memory) normalizeTar ↓ per entry: new tar.Header{Typeflag, Name(ToSlash, strip "./"), Linkname, ↓ Size, Mode, Uid:0, Gid:0, ModTime: zero} ↓ skip "" and "."; read data ↓ sort entries by Name; write a new tar sha256 → "sha256:<hex>" ↓ write layers/sha256_<hex>.tar if not present manifest{Config: empty Env/Cmd/WorkingDir, Layers: [{digest, size, "import <file>"}]} ↓ store.SaveManifest "Imported name:tag (layer sha256:<12 hex>, N bytes)"

What normalisation keeps and drops

Kept

  • Type flag (file, dir, symlink, hard link, devices…)
  • Name (slash form, no ./)
  • Link target
  • Size and mode
  • File data

Dropped / reset

  • Owner: uid/gid → 0, names dropped
  • mtime → zero time
  • Original entry order (re-sorted)
  • Extended headers not copied

This mirrors what CreateCopyLayer and CreateRunLayer do for built layers, so all layers follow the same "sorted, zero time, uid/gid 0" rule from the README.

Interview insight

An imported image has an empty config: no Env, no Cmd, no WorkingDir. That's why the sample Docksmithfile sets its own WORKDIR and CMD, and why docksmith run alpine:3.18 without a command fails with no CMD defined in image alpine:3.18 and no command given.

Why does import normalise the tar instead of storing it as-is?

Answer: So the digest depends only on the filesystem content, not on when or by whom the tar was made.

normalizeTar zeroes mtimes, sets uid/gid 0, strips ./ and sorts entries. Inference: two exports of the same image then normalise to the same bytes and the same layer file. Note the manifest digest still differs between imports because created differs.

What config does an imported image have, and what follows from that?

Answer: Empty: Env: [], Cmd: [], WorkingDir: "".

A Docksmithfile built FROM it inherits nothing, so it needs its own ENV/WORKDIR/CMD. Running it directly needs a command override; otherwise runtime.Run returns no CMD defined in image … and no command given. RUN steps still get a PATH because the builder adds a default one.

You import the same alpine-rootfs.tar twice under the same tag. What changes on disk?

Answer: The layer file is written once; the manifest is rewritten with a new created and therefore a new digest.

runImport only writes the layer if os.Stat says it's missing. The new manifest digest changes the first prevDigest of every build FROM this image, so the next builds miss the cache for their first COPY/RUN.

What is a cost of how runImport reads the tarball?

Answer: Memory: it loads the whole tar with os.ReadFile and holds every entry's data in a slice before writing a new tar into a bytes.Buffer.

Peak memory is roughly twice the tar size. Fine for Alpine (a few MB); a large rootfs would need a streaming approach, which sorting makes harder because all entries must be known before writing.

What does scripts/setup-base-image.sh do step by step?

Answer: Builds docksmith if missing, checks Docker exists, pulls alpine:3.18, exports a container's filesystem to a temp tar, imports it, and cleans up.

Commands: docker pull, docker create, docker export > alpine-rootfs.tar, docker rm, docksmith import -t alpine:3.18 <tar>, rm -rf $TMPDIR. It uses set -e, so any failure stops it.

Unit 4 · Topic 1

Runtime: from image to process

runtime/runtime.go (Linux only) turns a manifest into a running, isolated process. The binary runs twice: the parent prepares a root directory and starts a copy of itself in new namespaces; the child finishes the setup from inside and runs the command.

Parent side

Run(name, tag, envOverrides, cmdOverride)

  1. store.LoadManifest; command = cmdOverride if non-empty else Config.Cmd; none → no CMD defined in image n:t and no command given.
  2. Env map from Config.Env, then each -e override on top; add default PATH if missing.
  3. AssembleFilesystem(m): os.MkdirTemp("", "docksmith-run-*") + layer.ExtractLayers; defer os.RemoveAll.
  4. workdir = Config.WorkingDir or /; RunIsolated(root, cmd, workdir, env, false).

Why "re-exec yourself"?

Source says (README): "the binary re-executes itself with __child__ as the first argument inside new namespaces, then performs chroot". Inference: namespaces requested through clone flags apply to the new process, and the setup steps (mount proc, chroot, hostname, drop caps) must run inside them, before the user's command starts. A fresh copy of Docksmith is a convenient program to do that setup, with no separate helper binary.

Trace docksmith run myapp:latest from runtime.Run to the container's command.

Answer: Run → AssembleFilesystem → RunIsolated → (re-exec) → main → ChildProcess → command.

  2. AssembleFilesystem: extract all layers into docksmith-run-*

Inside a container you create /tmp/x. Does it appear on the host or in the image?

Answer: Neither, after the container exits.

The container's root is a temp copy made by AssembleFilesystem. The file exists in that host directory while the container runs, and defer os.RemoveAll(rootDir) in Run deletes it afterwards. Layers are never modified. This is demo step 8 in the README ("File must NOT appear on host").

What differs between how a RUN command and a CMD are executed?

Answer: The useShell flag and what happens to the root dir afterwards.

RUN: useShell=true, child runs /bin/sh -c "<joined args>", and the builder diffs the root to make a layer. CMD: useShell=false, child runs cmd[0] with cmd[1:] directly, and the root is deleted afterwards. Isolation is identical.

What does docksmith run -e GREETING=Goodbye myapp:latest change, and how?

Answer: The container sees GREETING=Goodbye instead of the image's Hello.

Run fills a map from Config.Env, then applies each override (split on the first =), so overrides win. The map becomes cmd.Env for the re-exec, and ChildProcess passes os.Environ() to the command. The image isn't modified.

The image's CMD points to a program that doesn't exist in the image. What error do you see?

Answer: child process error: … on stderr, then Container exited with code 1.

In ChildProcess, cmd.Run() fails with a non-ExitError (the program can't be found/started), so it returns the error; main prints child process error: %v and exits 1. The parent's RunIsolated sees exit code 1 and returns (1, nil).

Why does RunIsolated create proc, dev and the workdir inside the root before starting the child?

Answer: The child needs them to exist: proc is the mount point for the new procfs, and Chdir(workdir) fails if the directory is missing.

A WORKDIR that was never populated by a COPY or RUN isn't in any layer (COPY deliberately omits parent dirs), so it's created here. dev is created empty; no device nodes are added.

Which process is PID 1 inside the container's PID namespace?

Answer: Inference: the re-exec'd docksmith __child__ process, not the user's command.

It is the process created with CLONE_NEWPID, and ChildProcess starts the command with cmd.Run() (fork + exec + wait) rather than replacing itself, so the command is its child. One consequence: Docksmith's PID 1 only waits for that one child and doesn't reap other orphaned processes.

Namespaces, chroot & /proc

All namespace setup is in one function, isolationSysProcAttr(). It returns a syscall.SysProcAttr that tells Go to create the child process in new namespaces. Filesystem isolation is chroot, done by the child.

attr := &syscall.SysProcAttr{
    Cloneflags:   CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWNET,
    Unshareflags: CLONE_NEWNS,
}
if useUserNamespace {                       // default true; tests can turn it off
    attr.Cloneflags |= CLONE_NEWUSER
    attr.UidMappings = []SysProcIDMap{{ContainerID: 0, HostID: os.Getuid(), Size: 1}}
    attr.GidMappings = []SysProcIDMap{{ContainerID: 0, HostID: os.Getgid(), Size: 1}}
    attr.GidMappingsEnableSetgroups = false
}

chroot

syscall.Chroot(rootDir) makes the extracted directory the process's /; syscall.Chdir(workdir) then moves into the image's WorkingDir. From then on, /bin/sh means the Alpine shell inside the image. Source says (README Isolation table): "chroot — Filesystem rooted at assembled image layers".

chroot's known weakness

Inference: chroot only changes path resolution; a process that still holds CAP_SYS_CHROOT can escape it. Docksmith drops all capabilities right after chroot (next page), which removes that ability. The code uses chroot, not pivot_root.

Mounting /proc

Before chroot, the child runs syscall.Mount("proc", rootDir+"/proc", "proc", 0, ""). Inference: procfs shows processes of the PID namespace it was mounted from, so this mount is what makes tools like ps see only the container. It lives in the private mount namespace and disappears when the container exits. The mount's error is ignored.

Interview insight: under sudo

Inference: the README runs everything with sudo, so os.Getuid() is 0 and the UID map is "container 0 → host 0". The user namespace still exists, but container root is real root. The isolation benefit comes mainly from the capability drop.

Which namespaces does Docksmith create, and where in the code?

Answer: PID, mount, UTS, network and (by default) user, in isolationSysProcAttr() in runtime/runtime.go.

They are set as Cloneflags on cmd.SysProcAttr in RunIsolated, so the re-exec'd child is born inside them. IPC and cgroup namespaces are not used.

What do the UID/GID mappings say, in words?

Answer: "ID 0 inside the container is the host ID of whoever ran Docksmith; map just that one ID."

{ContainerID: 0, HostID: os.Getuid(), Size: 1} and the same for the GID. So the process is root inside its user namespace, and any file it creates on the host side is owned by the invoking user.

A Docksmithfile has RUN apk add curl. What happens?

Answer: It fails: the RUN runs with no network.

RunIsolated always sets CLONE_NEWNET, and nothing configures interfaces in the new namespace. apk can't reach its repositories, exits non-zero, and the build stops with step i/N: RUN command exited with code N. The README lists container networking as not implemented.

Why is /proc mounted inside the root, and why before chroot?

Answer: So the container sees a procfs for its own PID namespace; and before chroot because the path is given from the host side (rootDir/proc).

After chroot the same directory is /proc. Being in a new mount namespace keeps this mount out of the host's mount table. SnapshotDir and CreateRunLayer skip proc so it never ends up in a layer.

What does hostname print inside a Docksmith container, and why doesn't the host change?

Answer: docksmith; the change is confined to the container's UTS namespace.

ChildProcess calls syscall.Sethostname([]byte("docksmith")) after chroot. Because the child was created with CLONE_NEWUTS, it has its own hostname. The sample app's hello.sh prints it.

Why is there a useUserNamespace switch?

Answer: For tests: SetUseUserNamespace(false) lets the runtime test retry without CLONE_NEWUSER.

TestRunIsolatedBasic first runs with user namespaces; if the error mentions "operation not permitted" or "permission denied" it logs that user-namespace re-exec is unavailable and retries with it disabled. Production code never turns it off.

What would you add first to make Docksmith's isolation production-grade, based on what the README says is missing?

Answer: cgroups for resource limits and seccomp for syscall filtering, both listed as "Not implemented".

Without cgroups a container can use unlimited CPU/memory/PIDs. Without seccomp it can call any syscall its (dropped) capabilities allow. The README also lists overlayfs, volumes and networking as missing; those are features rather than isolation.

Capabilities & no_new_privs

runtime/isolation_linux.go has one function, dropCapabilities(), called by the child after chroot and hostname, just before it runs the command. It makes two raw system calls.

const prSetNoNewPrivs = 38
type capHeader struct { Version uint32; Pid int32 }
type capData   struct { Effective, Permitted, Inheritable uint32 }

// 1. prctl(PR_SET_NO_NEW_PRIVS, 1)
syscall.Syscall6(syscall.SYS_PRCTL, prSetNoNewPrivs, 1, 0, 0, 0, 0)
// 2. capset(hdr{Version: 0x20080522, Pid: 0}, [2]capData{all zero})
syscall.Syscall(syscall.SYS_CAPSET, uintptr(unsafe.Pointer(&hdr)), uintptr(unsafe.Pointer(&data[0])), 2)

What each call does

PR_SET_NO_NEW_PRIVS

Inference (Linux): a one-way flag inherited by children; after it is set, execve can't grant extra privileges (setuid binaries and file capabilities stop working).

Error: prctl(PR_SET_NO_NEW_PRIVS): …

capset to zero

Clears the effective, permitted and inheritable sets. Inference: version 0x20080522 is the kernel's capability API v3, which takes two 32-bit data structs (capabilities 0–31 and 32–63), hence [2]capData; Pid: 0 means the calling thread.

Error: capset: …

Source says (README): "child process maps container root to the host user and clears capability sets" and "Capability dropping and PR_SET_NO_NEW_PRIVS run in the child process."

Why raw syscalls?

Implementation shows the standard library has no capset wrapper and the project takes no dependencies, so the code lays out the kernel structs itself and passes pointers with unsafe.Pointer. The return of Syscall is (r1, r2, errno); a non-zero errno becomes the error.

Ordering in ChildProcess

mount proc → chroot → chdir → sethostname → dropCapabilities → run command ↑ needs privileges, so it happens before the drop
A subtle Go issue worth knowing

Inference: on Linux, capabilities and the no_new_privs flag belong to a thread, and Pid: 0 targets the calling thread. Go may move a goroutine between OS threads, and ChildProcess doesn't call runtime.LockOSThread(). So the later cmd.Run() could fork from a different thread that still has its capabilities. Locking the goroutine to its thread before dropCapabilities would make the drop reliable.

What does dropCapabilities do, and when is it called?

Answer: It sets PR_SET_NO_NEW_PRIVS and then clears the effective, permitted and inheritable capability sets with capset.

ChildProcess calls it after mount, chroot, chdir and sethostname and immediately before starting the command; a failure aborts with drop capabilities: ….

Why must dropCapabilities come after chroot and the proc mount, not before?

Answer: Mounting, chroot and sethostname are privileged operations.

Once the capability sets are empty, the child could no longer do them. So the order is: do all privileged setup, then drop everything, then run untrusted code. Inference: dropping after chroot also removes the ability to call chroot again, which is how chroot escapes work.

Why does the code pass [2]capData and version 0x20080522?

Answer: Inference: that is the layout the kernel expects for capability API version 3.

Linux has more than 32 capabilities, so v3 splits each set across two 32-bit words. All six words are zero here, meaning "no capabilities at all". Pid: 0 means the calling thread.

What does PR_SET_NO_NEW_PRIVS add on top of clearing capabilities?

Answer: Inference: it stops a later execve from gaining privileges back.

Without it, running a setuid program (or a binary with file capabilities) could raise privileges again. The flag is inherited by every descendant, so the user's command and anything it starts stay unprivileged.

Could the capability drop fail to apply to the user's command? How would you fix it?

Answer: Inference: possibly, because capabilities are per thread and Go can switch threads between the capset call and the fork in cmd.Run().

Fix: call runtime.LockOSThread() at the start of ChildProcess so setup, capability drop and fork all happen on one thread. Alternatively replace the child with the command via syscall.Exec on the same locked thread.

Error handling

Docksmith uses plain Go errors: functions return error, callers add context with fmt.Errorf("…: %w", err), and main prints the final message and exits 1. Container exit codes travel separately as integers.

The path of an error

Error condition e.g. RUN command exits 2 ↓ detection RunIsolated: cmd.Run() returns *exec.ExitError → (2, nil) ↓ representation builder: fmt.Errorf("step %d/%d: RUN command exited with code %d", …) ↓ propagation builder.Build returns it → main.runBuild returns it ↓ handling main: fmt.Fprintf(os.Stderr, "Error: %v\n", err); os.Exit(1) User sees Error: step 6/7: RUN command exited with code 2

Conventions in the code

  • Wrapping with context: store: read manifest n:t: %w; layer: extract layer sha256:…: %w; builder: every message starts step i/N:.

Why does RunIsolated return (code, nil) for a failed command instead of an error?

Answer: A non-zero exit is a normal outcome of running a program; an error means Docksmith itself couldn't run it.

What exactly does the user see if RUN false is step 4 of 5?

Answer: Step lines for 1–3, then Error: step 4/5: RUN command exited with code 1 on stderr, and exit status 1.

Name two places where Docksmith ignores errors, and the risk in each.

Answer: Examples: cache.loadIndex turns corrupt JSON into an empty index (risk: silent loss of all cache entries); extractTar ignores io.Copy/MkdirAll errors (risk: a truncated file in the container with no error).

Others: the proc mount and sethostname in ChildProcess, cache.Store's return value in the builder, and unreadable manifests in ListManifests.

If chroot fails inside the child, what does the user see?

Answer: child process error: chroot to <dir>: <errno>, then the parent reports exit code 1.

ChildProcess returns fmt.Errorf("chroot to %s: %w", …); the child's main prints it and exits 1; RunIsolated converts that to (1, nil). For run, main prints Container exited with code 1; for a build RUN, it's RUN command exited with code 1.

How does the builder make sure temp directories don't leak on a failed RUN?

Answer: Every error return after os.MkdirTemp is preceded by os.RemoveAll(tmpRoot), and the success path removes it after storing the layer.

The run path uses defer os.RemoveAll(rootDir) in runtime.Run instead. Inference: if the process is killed with a signal, neither runs, and the temp dir stays behind.

Pick one design decision in Docksmith and explain its trade-off.

Answer (example): Extracting layers into a temp directory instead of using overlayfs.

Why/how: ExtractLayers writes every layer into os.MkdirTemp for each RUN miss and each run; the README lists overlayfs as not implemented. Benefit: simple, no extra mounts, easy to inspect, container writes never touch stored layers. Cost: time and disk proportional to image size on every run and RUN.

Why chain the cache key on prevDigest instead of hashing each step independently?

Answer: A step's output depends on everything before it.

A RUN's result depends on the whole filesystem it starts from; hashing only its own text would reuse a stale layer after an earlier COPY changed. Including the previous digest makes the key represent "this step on top of exactly that state", and changes propagate automatically.

Compare how COPY and RUN layers are created.

Answer: COPY tars known files straight from the context; RUN runs a command in an isolated copy of the image and tars the difference.

COPY's key includes file hashes and it never needs Linux; RUN's key has no file hashes, needs the runtime, and is the only layer type that writes whiteouts. COPY omits parent directory headers; RUN writes them.

When would you use rmi and when prune?

Answer: rmi to delete a specific image (and the layers only it used); prune to clean up leftovers nobody references.

rmi removes one manifest and decrements only its layers. prune scans all layer files for zero references (failed builds, overwritten tags) and then removes cache entries pointing to deleted layers.

Why might Docksmith use JSON files rather than a database for its state?

Answer: Inference: the README's "No external dependencies: uses only the Go standard library" rules out an embedded DB, and encoding/json is in the stdlib.

Plus: human-readable during a demo (cat a manifest). Minus: cache.Store rewrites the whole index per entry, and there's no locking across processes.

How to talk about these

Lead with the mechanism ("the RUN diff compares content hashes only, so…"), give the concrete symptom ("the sample's chmod layer is empty"), and the fix ("snapshot mode too"). That shows you understand the code, not just the feature list.

Name the bug you'd fix first in Docksmith and justify it.

Answer (one good choice): the RUN diff ignoring mode changes.

It silently produces wrong images: RUN chmod +x script has no effect in the final image, and the sample app only works because CMD invokes /bin/sh explicitly. The fix is small and local: store hash + mode in SnapshotDir and compare both in CreateRunLayer.

Which listed non-features would matter most if Docksmith ran untrusted code?

Answer: cgroups and seccomp.

Without cgroups a container can exhaust host CPU, memory or PIDs. Without seccomp every syscall is reachable. Docksmith does have namespaces, chroot, and capability dropping, but the README lists both of these as not implemented.

Why could two builds of the same Docksmithfile produce different RUN layer digests?

Answer: Code-level reason: when a RUN deletes two or more directories, CreateRunLayer writes their opaque markers by ranging over a Go map, whose order is random.

Different order → different tar bytes → different digest. (The command itself could also be non-deterministic, e.g. writing a timestamp.) Sorting deletedDirs fixes the code part.

A project copies src/ containing a/index.js and b/index.js with COPY src /app/. What breaks?

Answer: Both files land at /app/index.js; the image keeps only b/index.js's content and the directory structure is gone.

CreateCopyLayer uses filepath.Base(relPath) for each file when the destination is a directory. Fix: compute the path relative to the source directory and join it to the destination.

Inside a Docksmith container, echo hi > /dev/null works but behaves oddly. Why?

Answer: /dev is an empty directory, so the shell creates a regular file named /dev/null.

RunIsolated only does MkdirAll(root/dev), and extractTar skips device entries from the base image. Output "discarded" to /dev/null is written to that file (inside the temp root, so it's deleted afterwards). The sample's whoami 2>/dev/null does this.
